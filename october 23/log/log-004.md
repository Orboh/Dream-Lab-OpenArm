# Log 004 — Dream docs via MCP, driver research, built-in OpenArm model (2026-10-23)

## Goal
Use the dreamlabs-docs MCP server to prepare the full DreamLab setup so the Dream web interface can be used.
Nothing was run on the arms; no driver file exists yet.

## Steps
1. `claude mcp list` shows dreamlabs-docs connected (the key is accepted). Its tools are not visible to this
   session until Claude Code restarts, so the docs were read by calling the server over HTTP with a small
   script in the scratchpad (`.../scratchpad/mcp.sh`; it reads the key from `~/.dreamlabs/credentials`, never prints it).
2. Read docs: "Driver template and examples" and "Your own robot". Downloaded Dream's example drivers to
   `~/my_robot/examples` (seeed_rebot, trossen) with the documented curl command.
3. The docs' rules for an agent, followed here: nothing that switches a motor on or sends a target is run by
   the agent (Arm, the wizard, runs without --dry-run); the dry run goes first on a ReadOnlyArm; the tool center
   point is measured by the user (`dreamcli tcp`), never guessed; `close()` never moves the arm.
4. Read the repo's robot side: the LeRobot fork (`~/projects/lerobot`, openarm_follower): Damiao motors, CAN ids 1-8
   (reply 0x11-0x18), models dm8009 (J1-2), dm4340 (J3-4), dm4310 (J5-7, gripper), MIT gains kp 240/240/240/240/24/31/25/25,
   kd 3/3/3/3/.2/.2/.2/.2; logical angle = native angle minus the homing offset in
   `~/.cache/huggingface/lerobot/calibration/robots/openarm_follower/follower_{left,right}.json`; gripper limits -65..0 deg
   (open = negative); CAN links are CAN-FD (`scripts/canup.sh`).
5. Dream ships a Damiao bus (`robots/damiao.py`) whose reply id is 0x10 + CAN id (same as OpenArm) but whose
   motor table only has the MakerMods Metal models; OpenArm's dm8009/dm4340/dm4310 ranges would have to be added.
6. Dream also has a built-in "Enactic OpenArm v2" model, `openarm2_faas` (beta_robots.json, body `custom`), which the
   Orboh repo already uses (`policy.ik_arm`). It may make the URDF upload and tool-point steps unnecessary.
7. Kinematics checks with the generated URDF: the right arm is the exact mirror image of the left (mirror about the
   base xz-plane, joint signs -1,-1,-1,+1,-1,-1,-1), so one arm model cannot describe both sides without a mirror step.
   Link lengths and joint limits of `openarm2_faas` equal the v10 chain, but joint axes and frame placement differ;
   my test of the joint-sign mapping between the two was flawed (invalid invariant) and settled nothing.
