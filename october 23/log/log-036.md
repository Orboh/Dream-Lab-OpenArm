## 4. The false "jump" stop: my bug from log-035
- In log-035 I moved the 20 deg wrong-mapping check so it looks at Dream's request before any safety cut. But I compared it with **the last target sent**.
- While the guard held the arm at the edge, Dream kept asking further (here: turning J7). The gap grew to 20 deg in about 1.3 s, and the check called it a wrong mapping and ended the run.
- **Fixed (tests first):** the check compares each request with **Dream's previous request** while that is fresh (0.5 s), and only otherwise with the last target or the arm (`_last_request`, `_refuse_a_jump(..., what)`).

## 5. The drop on Reset: the arm ended up deeper than the guard allows
- Measured right after the first Reset: grasp point 3.5 cm and housing 2.6 cm **inside** the table box, about 1.5 to 2.5 cm above the real table. Each further Reset: a little deeper (3.7 cm).
- **Cause, from the log timing and the code:**
  - Dream's Reset calls `torque_off()` on each arm, then opens it again.
  - `torque_off()` parks only an arm within 20 deg of its path (`PARK_TOLERANCE_DEG`). This one was 57 deg away, so the park was skipped and **every motor was switched off** (`openarm_v2.py` `torque_off`; `drops_when_limp = True`).
  - The arm fell until it rested on the table or the block. Dream reopened it about 30 ms later (new CAN socket 13:02:48.143), and it switched on **holding where it had fallen**.
- **Limit:** the driver logs no pose between 13:02:34 and 13:02:48, so the pose just before the Reset is not recorded. The code path and the timing fit the drop. This is the missing trace recorder (goal Gate 5).
- **Open, needs a decision:** a Reset (or `robot down`) far from the path drops the arm. Possible fixes:
  - a slow, damped release instead of an instant switch-off;
  - a way back to the path that is safe from any pose;
  - an operating rule: support the arm before Reset or stop whenever it is far from its path.
