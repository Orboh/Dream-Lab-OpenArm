## 2. Why the earlier plans failed
- Read-only driver and Dream's wizard: assumed the wizard can tell the two arms apart. It merged both followers: the two CAN channels of ONE PEAK adapter
  share a USB id. Worked around by naming the links (aliases left/right), not by the wizard.
- CAN and motors: assumed classic CAN and that a reply confirms "disabled". The robot needs CAN-FD; the reply carries the status from before the command
  (false "not confirmed" alarm). Fixed with a fresh state query.
- First station start: assumed starting leaves the arms safe. Dream refused the first live task ("unsafe instruction ... until stopped"): no zones, no bounded task.
- Safety area (capture, editor, zones): assumed region = bounding box of the recorded points with margin 0 is a good allowed area. Home sat 0.6-0.9 cm from
  the inner wall so any move away hit the edge; the table was a placeholder; no reference points; the zones were applied only at 17:22.
  Root cause: the region was derived from home and taught points instead of the work area; home was treated as a limit (the user: it is only the camera-view pose).
- Hard guard (fail-closed): assumed refusing a bad pose stops safely. The station ends a run on any ArmError, so a 0.1 cm overshoot killed 4 runs, and "arm already
  outside" blocked Home and Reset. Root cause: fail-closed with no way back. Fixed: cut the move at the edge, 2 cm slack on the measured pose.
- Round 7 smooth motion (tracker + control thread): assumed targets stay within 20 deg of the arm. The sanity check compared with the MEASURED arm while the
  tracker deliberately lags it, so longer moves died. A new part changed the meaning of an old check; found only on hardware. Fixed: step measured from the last target.
- One-arm lock: never set (no file = both arms active); Reset reopened both arms and swung the idle one. Dream has no per-arm setting and sends both arms every tick.
  The lock was built but was not part of the start routine. Fixed: a locked arm is not raised at open; the log shows what Dream asks of it.
- Park and stop: assumed any arm can be parked along the path. An arm more than 20 deg off the path is switched off where it is (limp, happened twice).
  Not fixed yet (P1.3 below).
- Cameras: preflight tested "plugged in", not "free". The editor held the RealSense cameras (exclusive), so the station quit. Fixed: new check names the holder.
- Tests: fakes and a simulated clock proved our code against our assumptions about Dream. Every live failure was an interaction no fake modelled
  (Dream's Home/Reset, tracker lag vs sanity checks, run timing, camera exclusivity).
- Latency: assumed the model answers in about 0.5 s. Median round trip is 1.27 s over the day and 2.4-2.7 s since about 15:00 local (UTC 06:00):
  our network about 70 ms, Dream's gateway 1-2.2 s, model inference about 0.48 s. At 2.7 s chunks land near the 3.0 s action_timeout_s and some are discarded.
Systemic causes: (1) Dream's behaviour checked in its code late (per-arm selection, Reset, the linear 3 s Home blend); (2) safety rules built fail-closed with no way back;
(3) data derived from taught points without margin; (4) too much verified offline, first contact with the real station late; (5) no standing measurement of
latency or of what Dream asks of each arm until round 7 added the request log.

## 3. The CAN / one-USB hypothesis: answer
`can_fol_l` and `can_fol_r` are the two channels of ONE PEAK PCAN-USB Pro FD (USB 1-1); `can_lead_l` and `can_lead_r` are the two channels of a second
adapter (USB 1-7). Each channel has its own controller and bus, so this is not a broadcast.
Evidence: listen-only reads heard 8 motors on each follower link, with different poses (left [44.7, -4.5, ...], right [-44.2, -2.5, ...]).
The single adapter does cause one thing: Dream's setup wizard sees one USB id and merges the arms (already worked around).
A broadcast would exist only if both arms were wired to the same channel (motor ids 1-8 would collide). P0 proves they are not.

## 4. The main plan (recommended, in order)
P0 Prove the CAN buses are separate (needs the user's OK: one query frame is sent)
- New listen-only preflight check "each follower link hears only its own 8 motors" (`workspace/canobserver.py` PassiveArm).
- One controlled read-parameter query to ONE motor: the frame appears on its link only; repeat for the other arm.
- If a frame ever appears on both links: stop; fix wiring and termination (120 ohm per bus) before anything else.
P1 Make collisions impossible by construction
1. Arm-against-arm guard: a process-wide registry of each arm's link points (both arms run in the one station process), checked in `Guard.limit`; tests first.
2. A new home with each hand 10-15 cm to its own side (the user records with the leader in the editor); `region_overlap_cm()` must read 0 on the Save card.
   The 18:02 bundle (overlap 8.9 cm) is NOT applied until then.
3. `Arm.stow()`: an arm that is off the path returns slowly through the guard, else it holds and raises `alarm()` instead of being switched off limp.
4. `arms.py auto`: picks the arm by the block's side and locks the other at rest (a locked arm already stays still and unraised).
P2 Latency and timing
- Measure rtt and gateway by hour from `~/robots-inference.jsonl`; report to Dream if the gateway stays above 1.5 s.
- Station file through `zonebuild.GENTLE_STATION`: `action_timeout_s: 6.0` and the derived `max_stall_ticks`; keep `ramp_s 3`, `max_ee_speed_m_s 0.15`.
- Preflight prints the median rtt and warns above 2 s. Do not cut cameras or image size blind: the model was trained on its camera set.
P3 Scene and calibration
- Place the real table from two touched reference points per arm, `verify` within 2 cm; set the block's start area; confirm the head camera frames table and block.
- Record the arm-base height against the table (coworker's twin: 0.298 m; our body-frame shoulder z is 0.698) and settle any mismatch.
P4 Base-model ladder (one arm unlocked, hand on the emergency stop; read the "Dream asks" log lines and the saved episode after each step)
1. "move the gripper above the wooden block"  2. "open the gripper" / "close the gripper"  3. "move down to the wooden block and close the gripper"
4. "pick up the wooden block and lift it 10 cm"  5. "pick up the wooden block and put it in the box" (only after 3 of 5 on step 4).
Pass: moves toward the block, no guard refusal, closes on it, lifts it, stays inside the zones. Write each trial (prompt, result) in the next log.
Gate: if direction words are not followed 5 of 5 times in steps 2-3, go to another plan in section 5.

## 5. The other plans (for the user's own research)
5.1 Fine-tune Dream-1 on your own demonstrations (the natural next step if P4 fails)
- Steps: collect 30-50 teleop episodes of "pick up the wood" with the coworker pipeline (openarm-orboh, branch `feat/takeei-wood-l1`; 8 good episodes exist,
  start-pose hold on); convert them to embodiment `koutaueda/openarm2-faas` (state/action spans including the six EEF parts, because the station uses the
  `eef` head; video roles head/wrist_l/wrist_r); `DreamClient.validate_dataset` locally; `upload_dataset`; `finetune(use_eef=True, lr_schedule="cosine")`;
  then `checkpoint: dream-1-ft:...` in `station.yaml`.
- Pros: the only route to a model that knows this robot and this block. Cons: data time, cost; Dream's doc says specialist tasks "may not be highly reliable yet".
- Research: the embodiment config registered on the account; price and queue (`fine_tuning.queue()`); how many episodes others needed; whether the 8 existing
  episodes already match the embodiment layout.
5.2 Classical pick, with Dream only as the language front-end
- The coworker's parked grasp planner (`orboh/planning/grasp.py`, work/18), depth block finder (work/16), camera-to-base calibration (about 25 mm, work/17).
- Pros: deterministic, no model latency. Cons: unfinished, does not use Dream's power, needs the calibration to hold; the station would only trigger it.
- Research: how the planner's output can drive our driver (a custom driver call versus Dream's policy loop); what accuracy a 25 mm calibration allows for a block.
5.3 Hybrid: Dream-1 brings the hand near the block, a short scripted grasp finishes it (descend, close, lift)
- Pros: Dream where it is strong (scene understanding), script where it is weak (grasp). Cons: two systems and a handover; needs a block position from depth.
- Research: whether a bounded prompt can hand control to a script safely; what the grasp needs (approach height, gripper contact angle about -32 deg from the demos).
5.4 A one-arm station (only one follower in `station.yaml`)
- Would remove the idle arm entirely. Unknown whether Dream's custom body accepts one arm or the embodiment needs both.
- Research: `robots/config.py` and the embodiment definition. The lock plus `arms.py auto` in P1.4 is the fallback.
5.5 Hardware changes (a second PEAK adapter per arm, shorter or terminated cables)
- Not needed if P0 shows separate buses; consider only for noise or error counters (`berr-counter` in `ip -d link show`).
5.6 Ask Dream for faster serving, or another region
- The latency is gateway-side; send support our measured numbers (section 2, Latency). No code change.
