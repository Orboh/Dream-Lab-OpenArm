# Log 005 — OpenArm driver for the Dream setup (2026-10-23)

## Goal
The user's robot is OpenArm v2 and the setup wizard (model: Enactic OpenArm v2) needs a driver class. Write it.
Nothing was run on the real arms; only a fake CAN bus was used.

## Decisions
- Dream's docs ship every driver as two classes: a read-only one for the dry run (opens the arm, switches no motor on,
  refuses write) and the full one. Both were written; only the read-only one is meant to be tried first.
- Not the LeRobot fork's connect()/disconnect(): the fork's connect() moves both arms (startup alignment).
  The driver uses Dream's own Damiao bus (`robots.damiao`), whose reply id (0x10 + CAN id) matches OpenArm's.
- Motor ranges for DM8009 / DM4340 / DM4310 were added to Dream's table from the fork's `motors/damiao/tables.py`
  (Dream's table only has the MakerMods Metal models).
- Angles: native degrees minus the fork's `homing_offset` (follower_left/right.json) = logical degrees (zero = hanging down);
  refuses to open without that file. Gains and joint limits are the fork's.
- Joint mapping to Dream's `openarm2_faas` model is the IDENTITY and is NOT VERIFIED. My attempts to derive the signs
  from the two URDFs were inconclusive (position tests cannot tell a mirror from the real thing; the orientation test
  disagreed for every sign choice). It has to be checked on the arm with the read-only class.
- Safety in the full class: first target of every motor is its own position; refuses a target more than 20 deg from the
  arm, clamps to limits, refuses to write until the gripper's closed/open angles are measured, confirms each motor
  switched on/off, close() never switches motors off, torque_off() does not park (the arm falls: support it).

## Files
- `october 23/driver/openarm_v2.py` — classes `ReadOnlyArm`, `Arm`.
- `october 23/driver/test_openarm_v2.py` — 16 tests on a fake CAN bus (no hardware). Result: 16 passed.
  Run: `cd "october 23/driver" && env -u PYTHONPATH -u AMENT_PREFIX_PATH PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 ../../.venv/bin/python -m pytest -q test_openarm_v2.py`
  (the ROS environment in the shell breaks pytest's plugin loading otherwise).

## Not verified
- Real CAN traffic (CAN-FD links carrying classic frames), real motor replies, motor CAN timeouts, the joint mapping,
  the gripper angles, how the wizard uses the class in later steps.

## Addendum — CAN-FD (found at wizard step 3, "Connect arms")
- The wizard showed all four CAN links (can_fol_l/r, can_lead_l/r) down and suggested
  `sudo ip link set <link> up type can bitrate 1000000` (classic CAN). By then `can_fol_l` was already up as classic 1 Mbit.
- The fork runs OpenArm on CAN-FD (`use_can_fd: True`, `can_data_bitrate` 5 Mbit; `scripts/canup.sh` in openarm-orboh
  configures 1M/5M with `fd on`). Dream's Damiao bus sends classic frames and opens the link without `fd=True`.
- Driver fixed: `open_fd_bus` (python-can socketcan, `fd=True`) and `FdBus` (sends `is_fd=True` frames, no bit-rate
  switch, as the fork does). New test: every frame sent is an FD frame. 17 tests pass (fake bus).
- Action for the user: bring the links up with `cd ~/projects/openarm-orboh && sudo bash scripts/canup.sh` (FD), not the
  wizard's classic command. Tick only the follower adapters in the wizard, not the leaders.
- Still unverified on real motors: that they answer these FD frames through this path.
